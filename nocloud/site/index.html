How it works

Three steps. No account, no upload, no wait.

  1. 1

    Drop a file

    Drag any file — or a whole folder — onto the window. It stays on your disk; nothing is copied to a cloud. Optionally type a passphrase to lock it end-to-end.

  2. 2

    Get a code

    You get a short share code (or a Tor address, or a plain web link — your choice). The code is the file's content address; there is no upload step to wait for.

  3. 3

    Send the code

    Message the code to your friend however you like. They paste it in and the file streams directly from your machine to theirs, resuming if the connection drops.

Three ways to share

Pick the trade-off you want — and know exactly what it hides.

"No cloud" is not the same as "anonymous," and not the same as "encrypted." Those are three separate switches. Here is the honest breakdown of each path.

Share code

BitTorrent over the DHT

A ~40-character code that is the file's info-hash. No tracker, no server — the distributed hash table introduces your machine to whoever pastes the code. Resumes if interrupted.

  • IP hiddenNo — visible to peers
  • EncryptedOptional (passphrase)
  • Recipient needs appYes
Private / Tor

An onion stream, both ends hidden

The bytes ride a Tor onion service. Both your IP and the recipient's are hidden, and no torrent is ever created. The anonymous path, for when who is sharing matters as much as what.

  • IP hiddenYes — both ends
  • EncryptedOptional + authenticated
  • Recipient needs appFile: yes · link: no
Web link

A plain link, any browser

An ordinary http:// link that opens with no app on the other end. Serve a file, a folder, or a whole website. The router port opens automatically over UPnP / NAT-PMP.

  • IP hiddenNo — link exposes it
  • EncryptedNo — plain HTTP
  • Recipient needs appNo — any browser

Any file can be locked with a passphrase (optional): the network only ever sees ciphertext under a neutral name, and a wrong passphrase is caught before anything downloads. The exact model is in what-it-hides.md.

Everything it does

Small app, serious capabilities.

End-to-end encryption

A passphrase derives a key with Argon2id and seals the file with libsodium's authenticated crypto_secretstream. Truncation is detected on decrypt; a wrong passphrase never downloads a byte.

No size limit, ever

Multi-gigabyte files move one bounded slice at a time, straight between disks. The payload never crosses into the interpreter, so the app's memory stays flat whether it's a photo or a film.

Tor anonymity, built in

The Private path runs the transfer over a Tor onion service, hiding both IP addresses and creating no torrent at all. It fails closed: no Tor, no leak — the other two paths just keep working.

Streaming & seeking

The built-in web host speaks HTTP Range, so a browser can stream and scrub a video or track without downloading the whole file — served one memory-flat slice per write, with natural backpressure.

Host a whole website

Point the web link at a folder and it serves a real site — SPA routing, forced downloads, correct MIME, custom API routes from a drop-in .qsroutes.json, and a LAN-only admin panel to edit it live.

Self-contained & standalone-ready

One stack script builds its own UI on every launch — nothing to persist. Package it as a native .exe / .app / Linux binary for Windows, macOS and Linux with no native code to compile.

What each path hides — and what it doesn't.

Nothing here is marketing. Where a protection doesn't apply, it says so.

Two questions decide everything: can someone see your IP? (only Tor hides it) and can someone read the bytes? (that's the separate encryption switch). A path can do one, both, or neither — so check, don't assume.

Under the hood

For the people who read the source.

No Cloud Quick Share is a single OpenXTalk / xTalk stack script — a binding consumer that calls into prebuilt, battle-tested extensions. There is no native code in the app itself, and no build step for the logic.

  • Fail-closed by design. Every optional extension is probed once at startup into a boolean and never called outside its guard. Missing SodiumXT? Encryption is simply off and everything else works. Missing Tor? The other two paths carry on.
  • Single-threaded, on purpose. Script, the FFI and rendering share one interpreted thread. Inbound BitTorrent events are poll-drained off a 250 ms timer, so no engine callback ever runs app script — the discipline that keeps it stable.
  • Payload never crosses the FFI. Gigabytes move engine ↔ disk on the extension's own threads; the app only issues tiny commands and reads small status records.
  • Versioned, authenticated wire formats. Encrypted codes carry a magic prefix (BTXQS1: / BTXTOR1:); an old reader rejects an unknown format cleanly rather than mis-parsing it.
  • Verifiable off-engine. A static linter and a pure-logic "golden" pin the security-critical helpers (range parsing, path confinement, MIME, header sanitising) in plain Python, so a regression is caught before it ships.
  • Extends the family. It stands on the same OpenXTalk extensions its siblings do — TorrentXT, SodiumXT, OnionXT — sharing their hard-won safety rules.

As a standalone app

In the standalone builder, include TorrentXT (required) and — for the optional features — SodiumXT, OnionXT, the Internet library and the JSON library. Every one fails closed, so it's safe to ship with or without them.

No other inclusions, externals, fonts or native resources are needed. Ships for Windows, macOS and Linux; downloads land in Documents/No Cloud Quick Share.

Questions

The things people ask.

Is it really peer-to-peer, with no server?

Yes. On the Share-code and Tor paths there is no server and no tracker — your machine talks to the recipient's directly (the DHT or a Tor onion just introduces them). The Web link runs a tiny HTTP host on your own machine; the file still never leaves it until someone fetches it.

Does "no cloud" mean it's anonymous?

Not by itself. A direct connection means the other side sees your IP — that's only hidden on the Tor path. And encryption is a separate switch (a passphrase). The transparency table spells out exactly what each path does and doesn't hide.

What's the largest file I can send?

There's no built-in cap. Files stream one bounded slice at a time straight between disks, so a multi-gigabyte transfer uses the same flat memory as a small one. The practical limit is your disk and your connection.

Do I need to install anything special?

To send, you run the app. To receive: a Share code or a single Tor file needs the app too; a Web link opens in any browser with nothing installed. The Tor path additionally needs a local Tor daemon on the sending machine.

Can I host a website or an API from a folder?

Yes — that's what the demo web app shows. Share a folder over a web link and it serves a real SPA (routing, Range streaming, forced downloads), plus custom endpoints from a drop-in .qsroutes.json and a LAN-only admin panel for editing it live.

What's the license?

MIT. The whole thing is one readable OpenXTalk stack script plus a small bundled web app — fork it, audit it, ship it.
