# The Riptide Protocol

**A serverless social protocol: identity is a key you hold, following is
knowing a key, reaching someone is verifying them.** This document is the
implementation-neutral specification of everything that crosses a wire or
a disk boundary in Riptide, written so that an implementation in any
language can interoperate with any other. The reference implementation is
`riptide/src/riptide.livecodescript` (pure LiveCodeScript over the
OpenXTalk suite extensions); the conformance oracle is
`riptide/tools/riptide_reference.py` (pure Python, stdlib only); and the
machine-readable test vectors are `riptide/docs/protocol-vectors.json`,
generated from the oracle and regenerated by
`riptide/tools/export-protocol-vectors.py` on every push.

**Status and evidence.** This specification was extracted from the
implementation on 2026-08-29, not designed ahead of it, and each rail
carries the evidence its implementation earned: the feed, media and DM
rails have run end to end between two real machines; the LAN and anon
compute layers are engine-verified with their live legs scripted and
pending; the Nostr rail is executed headlessly against real libsecp256k1.
`riptide/CLAUDE.md` and `docs/OXT-PASS-RUNBOOK.md` hold the dated
records. Nothing in this document upgrades any of those labels.

**Normative language.** MUST and MUST NOT are interoperability and
security requirements. SHOULD marks application policy the reference app
follows and a conforming implementation is strongly advised to follow;
deviating changes user-facing safety, not wire compatibility. Byte
layouts are normative to the byte.

**Versioning.** Every record format begins with a magic that IS its
version. Any change to a format's framing MUST mint a new magic
(`RSH1` -> `RSH2`); a silent framing fix under an existing magic is
forbidden. Parsers MUST refuse an unknown magic. Unknown KIND bytes,
unknown flag bits, and trailing bytes are refused fail-closed, so the
formats are closed to extension by design: extension happens by new
magic, new kind registered here, or a new BEP44 salt - never by
tolerated slack in an existing parser.

## 1. Primitives

Every primitive is a published algorithm with implementations in every
mainstream ecosystem. Names in parentheses are the libsodium spellings
the reference stack calls through SodiumXT.

| Purpose | Algorithm |
|---|---|
| Identity and record signatures | Ed25519 (`crypto_sign`, detached) |
| Subkey derivation | BLAKE2b keyed KDF (`crypto_kdf_derive_from_key`) |
| General hashing | BLAKE2b (`crypto_generichash`), lengths 16..64 |
| Key-file and app-state sealing | Argon2id (`crypto_pwhash`) + XSalsa20-Poly1305 (`crypto_secretbox`) |
| DM session agreement | X25519 (`crypto_kx`) |
| DM transport encryption | XChaCha20-Poly1305 secretstream (`crypto_secretstream`) |
| First-contact sealing | sealed box (`crypto_box_seal`) |
| Nostr identity and signatures | secp256k1 / BIP-340 Schnorr |
| Nostr rail auxiliary hash | SHA-256 |
| Onion address | SHA3-256 + RFC 4648 base32 (lowercase, no padding) |
| DHT immutable targets | SHA-1 over the bencoded value (BEP44's own rule) |

The KDF call is exactly libsodium's: `BLAKE2b(out=len, key=master,
salt=LE64(subkey_id), personal=context)` over an empty message. The
oracle pins this against sodiumxt's C KAT at import and refuses to load
on disagreement - an implementation SHOULD anchor its KDF the same way
before trusting anything derived below.

## 2. Identity and the subkey tree

A user is a single 32-byte uniformly random **master seed**. Everything
else derives from it through the KDF with the 8-byte context
`"riptide\0"` (the ASCII bytes of `riptide` followed by one NUL):

| Subkey id | Length | Purpose |
|---|---|---|
| 1 | 32 | the ed25519 identity seed (the public identity) |
| 2 | 32 | the DM crypto_kx seed |
| 3 | 32 | the shared LAN-mesh ed25519 seed |
| 4 | 32 | the Nostr secp256k1 secret key candidate (see 2.3) |
| 5 | 32 | the app-state sealing key (RIPTAPP1) |
| 100+n | 32 | anon persona n's ed25519 seed |
| 200+n | 32 | anon persona n's sealed-DM kx seed |

One seed never feeds two cipher schemes: every new use of the master
MUST take a new registry row here, never reuse an existing subkey.

**2.1 The handle.** The user's public identity is the ed25519 public key
of subkey 1, spelled as 64 lowercase hex chars - the **handle**. It is
simultaneously the BEP44 mutable-item public key their feed publishes
under (BEP44 signs with the same ed25519).

**2.2 The onion spelling.** The same 32 public-key bytes spelled as a
Tor v3 onion address:
`base32_lower(pubkey || checksum || 0x03) + ".onion"` where
`checksum = SHA3-256(".onion checksum" || pubkey || 0x03)[0:2]` - 56
base32 chars before the suffix. The first 32 decoded bytes invert the
mapping offline.

**2.3 The Nostr key ladder.** A secp256k1 secret key must lie in
`1..n-1`; a KDF output is 32 uniform bytes. The candidate is subkey 4;
while it is out of range, re-hash with SHA-256, at most **8** rungs,
then refuse. (No real master reaches rung 2; the bound exists so the
untakeable branch is testable - the all-zeros candidate and the group
order n are both pinned vectors.) The Nostr public key is the BIP-340
x-only key; the npub is its NIP-19 bech32 encoding.

**2.4 The sealed key file (RIPTKEY1).** The master seed at rest,
**exactly 97 bytes**:

    "RIPTKEY1" "E"  salt(16)  secretbox(seed32)

where the secretbox blob is `nonce(24) || ciphertext(32) || mac(16)` and
the wrap key is `Argon2id(passphrase_utf8, salt, out=32, opslimit=2,
memlimit=interactive)`. The salt is fresh random per seal. A parser MUST
refuse any other total length before touching crypto. Both ends must
agree on the Argon2id parameters; these are the ones every sealed file
in the reference family uses.

**2.5 The sealed app state (RIPTAPP1).** `"RIPTAPP1" "S"` followed by
`secretbox(state_utf8, subkey5)`; the plaintext caps at 1,048,576 bytes
and MUST round-trip as valid UTF-8 (decode, re-encode, compare - decode
alone is lossy on some runtimes and MUST NOT be trusted to throw). The
payload text is application-owned, deliberately outside this spec: the
envelope is the contract, the contents are not.

## 3. Conventions shared by every record

- Multi-byte integers are **big-endian**; u64 travels as two u32 halves
  (hi, lo).
- DHT targets and torrent info-hashes travel as **40 ASCII lowercase hex
  bytes**; the all-zeros target means "none". Handles and public keys as
  **64 ASCII lowercase hex bytes**; the all-zeros handle means "none".
- Kind bytes compare **byte-exact**: `"d"` is not `"D"`. (The reference
  dialect's string equality folds case; any implementation whose default
  compare does the same MUST compare bytes here.)
- Caps refuse, never truncate, on build AND parse; parses are strict to
  the byte (declared lengths must consume exactly the record; trailing
  bytes are refused).
- Text fields are UTF-8 and MUST be validated by round trip on parse.
- Ed25519 signatures are detached, 64 bytes, always over every byte of
  the record before the signature (plus a domain prefix where one is
  specified).

## 4. The public feed (the DHT rail)

### 4.1 RSH1 - the feed head

The single mutable anchor of a user's feed. BEP44 mutable item, public
key = the handle's key, salt = `"riptide-head"`.

    "RSH1"  seq(u64)  nameLen(u8) name  latestPostTarget(40 hex)
    prekeyTarget(40 hex)  onionLen(u8: 0 or 62) onionAddr
    profileMetaTarget(40 hex)

Caps: name 0..64 UTF-8 bytes; the whole record inside the BEP44
1000-byte value cap. `seq` MUST equal the BEP44 sequence number the item
is published under; an ingester MUST refuse a head whose embedded seq
disagrees with the BEP44 seq it arrived under, and MUST verify the
BEP44 signature itself with the handle's key rather than trusting the
transport.

On the DHT the stored value `v` is the **bencoded byte string** of the
record (`<len>:<bytes>`), and the canonical signing buffer is BEP44's:
`4:salt12:riptide-head3:seqi<seq>e1:v<bencoded v>`. The head signature
is ed25519 over exactly that buffer.

`profileMetaTarget` names an immutable item whose value is the display
name's raw UTF-8 bytes (1..64); content addressing extends the head's
signature to it. Readers verify the returned bytes' SHA-1-of-bencoding
against the target before believing them.

### 4.2 RSP1 - the post record

An immutable BEP44 item (target = SHA-1 of the bencoded value), 1..1000
bytes:

    "RSP1"  timestamp(u64, unix seconds)  prevPostTarget(40 hex)
    kind(1 byte)
      kind "D": textLen(u16) text(UTF-8)
      kind "C": chunkCount(u8, 1..16) then chunkCount * 40-hex targets
    mediaCount(u8, 0..8) then mediaCount * 40-hex torrent info-hashes
    authorSig(64)

`authorSig` is ed25519 by the identity key over every byte before it.
Posts form a hash chain: `prevPostTarget` walks back to the all-zeros
target. **A reader MUST verify the author signature and recompute every
content address before rendering anything**; a verified feed IS a
verified chain walk.

Kind D carries text directly; its capacity beside `m` attachments is
`1000 - 120 - 40*m` bytes (the layout arithmetic; publish this as API,
never hand-copy the number). Kind C carries the text as 1..16 immutable
chunk **values** (raw UTF-8 bytes, split by byte - a boundary may fall
inside a UTF-8 sequence). The reassembler MUST validate content
addresses per chunk and UTF-8-round-trip the **concatenation**, never a
chunk alone. Any split of the same bytes reassembles identically; full
1000-byte chunks are the reference policy.

### 4.3 Media

An attachment is a **single file** seeded in place as a trackerless
BitTorrent v1 torrent; its 40-hex info-hash is both the content address
(verified piece-by-piece by the fetching client) and the fetch linkage
(DHT swarm / magnet). Fetchers SHOULD download sequentially and MAY
begin playback mid-download.

## 5. Direct messages (the rp1 rail)

### 5.1 Rendezvous derivations

- `inboxId(handle) = BLAKE2b-20(pubkey_bytes || "riptide-inbox")` as 40
  hex - a phantom (contentless) swarm identifier where strangers reach
  a user.
- `roomId(pkA, pkB, salt) = BLAKE2b-20(sortedConcat(pkA_bytes,
  pkB_bytes) || salt)` - sorted by lowercase-hex order, which equals raw
  byte order, so both peers derive the same id; the salt is
  session-scoped application data.

### 5.2 The transport

DM bytes ride **rp1**, torrentxt's BEP10 peer-wire extension (extension
name `rp1`), which moves opaque messages up to 60,000 bytes between
peers of a swarm and carries an optional opaque `rp1_tok` blob in the
extended handshake. Any BitTorrent stack with BEP10 support can
implement it; `torrentxt/docs/api-reference.md` section "rp1" is its
wire description. Peers meet in the recipient's inbox swarm.

### 5.3 RSK1 - the signed prekey

**Exactly 132 bytes**: `"RSK1" kxPub(64 ascii hex) authorSig(64)`, the
signature by the identity key. Published as an immutable item; the head
advertises it via `prekeyTarget`. This is what makes first contact
sealable to a key that **provably belongs to the recipient** - a sealed
box needs an X25519 key, an ed25519 handle is not one, and no conversion
is used; the prekey record bridges the two key worlds under a signature.

### 5.4 RSI1 - the sealed intro

The first-contact plaintext, **exactly 268 bytes**:

    "RSI1"  senderHandle(64 hex)  senderKxPub(64 hex)
    recipientHandle(64 hex)  timestamp(u64)  authorSig(64)

signed by the sender's identity key, then sealed (crypto_box_seal, +48
bytes) to the recipient's **prekey** kx public. The recipient handle
inside the signed body binds the intro to one inbox - replaying it to a
third party dies on that check. Recipients MUST verify the signature,
the recipient binding, and SHOULD apply a freshness window (the
reference: +-600 seconds).

### 5.5 RSM1 - the transport frame

`"RSM1" kind(1) payload(1..59995)`, whole frame within the rp1 60,000
cap. Kinds, byte-exact: `I` = a sealed intro; `H` = a secretstream
header; `M` = stream ciphertext.

### 5.6 The session

Roles are decided by handle order: the **lexically smaller handle is
the crypto_kx client**. Each side derives (rx, tx) with crypto_kx from
its DM keypair (subkey 2) and the peer's kx public (from the intro or
prekey); my tx is your rx by construction. Each direction is its own
secretstream: send your header in an `H` frame, then messages as `M`
frames. Peers are authenticated by what only they can do - produce
ciphertext the derived session accepts; the first failed pull drops the
peer. A hang-up sends one final message with the secretstream FINAL tag
(body is filler, at least one byte; the tag is the message).

The plaintext inside the stream:

    kind(1: "T" text / "O" SDP offer / "A" SDP answer)
    timestamp(u64)  body(UTF-8, non-empty)

`O`/`A` carry WebRTC SDP for the call rail: signalling rides the
already-authenticated DM session, STUN only, no TURN by design (a
symmetric-NAT pair fails visibly rather than relaying silently).

## 6. The LAN device mesh (the enet rail)

All of one user's devices share the master seed, so all derive the SAME
ed25519 keypair from subkey 3. Admission proves possession of the
master; it is deliberately NOT a per-device identity. Transport is
enet (reliable channel 0, plus channel 1 for presence, sent
unsequenced); the enet connect rider u32 is a protocol tag only.
Records are authenticated, NOT encrypted - a LAN observer reads draft
plaintext, and implementations MUST say so in their UI.

All RSL1 records: `"RSL1" kind(1) nameLen(u8) name(1..32 UTF-8) ...`
Device names are display labels; any admitted device can sign any name
(the threat model is your own devices).

| Kind | Body after name | Signature |
|---|---|---|
| `C` challenge | nonce(32, fresh random) | none |
| `R` response | sig(64) | ed25519 over `"riptide-lan" \|\| nonce \|\| joinerName` |
| `W` welcome | sig(64) | ed25519 over `"riptide-lan-w" \|\| responseSig \|\| hostName` |
| `D` draft | seq(u64) draftLen(u16) draft(0..4096 UTF-8) | see below |
| `F` feed state | feedSeq(u64) readPeer(64 hex or zeros) readUpTo(u64) | see below |
| `P` presence | flags(u8: bit0 typing; other bits MUST refuse) tick(u64) | see below |
| `M` media handoff | seq(u64) infoHash(40 hex, non-zero) fileNameLen(u8) fileName(1..255) fileSize(u64) | see below |

The welcome makes admission **mutual**: it signs over the joiner's own
response signature (unique per nonce), so it replays to no other
handshake, and only a master-holder can produce it.

The four sync kinds (`D`/`F`/`P`/`M`) sign ed25519 under the shared LAN
key over `"riptide-lan-s" || the whole record body` (kind byte
included). Every record is **absolute state**, never a delta; replay
and reorder are neutralized by apply semantics, not by the wire:
drafts and handoffs apply only at a strictly higher per-**device** seq
(keyed by the signed name, not the transport peer - a host relays
verified records verbatim, so one link can carry many devices), feed
state applies as max, presence at a strictly higher tick. Counters
SHOULD seed from the clock so restarts stay monotonic. `M` is a
pointer: the bytes ride the section-4.3 media rail; bulk never crosses
enet (over the 60,000-byte seam a payload stops being a message and
becomes a torrent).

## 7. The anonymous persona (the onion rail)

Persona n is a separate ed25519 identity (subkey 100+n), reachable ONLY
as a Tor v3 onion service whose service key IS the persona key - so
`anon_onion(master, n)` derives offline, and reaching the onion verifies
the key. **The transport policy is normative** (the deanonymization
guard): an anon persona MUST use only the onion transport - it MUST
NOT touch the DHT, seed or fetch a torrent, open an rp1 or LAN or
WebRTC or Nostr channel. The public identity may use anything BUT
onion serving. Unknown transports MUST refuse for both. Implementations
MUST route every transport decision through one policy function so the
matrix cannot drift per call site.

Serving over the onion (HTTP; bodies are hex text so they survive every
client untouched):

- `GET /` - the anon feed page: deterministic UTF-8 HTML built from
  (title, entries), entries HTML-escaped (`&` first, then `<`, `>`,
  `"`), page capped at 65,536 bytes. The page is a wire format, pinned
  byte-for-byte; a look change is a deliberate re-pin.
- `GET /prekey` - the persona's RSK1 record (kx public = subkey 200+n,
  signed by the persona identity) as exactly 264 lowercase hex chars.
- `POST /dm` - the body MUST be exactly 632 lowercase hex chars (the
  48-byte seal + 268-byte intro, hex-doubled); anything else is refused
  before decoding, and every refusal returns the same reply so the
  route is not an oracle.

Bulk transfer over an onion stream uses **BTXO** framing (shared with
the family's quickshare): header `"BTXO" ver(1=0x01) flags(1)
nameLen(u16) name total(u64)`, then data frames `len(u32) bytes`
(non-empty), terminated by a zero-length frame. Caps at the receiver:
name 1024 bytes (refused from the first 8 header bytes), total 8 GiB,
frame 65,536.

## 8. The Nostr bridge (the reach rail)

Nostr is reach, never a dependency: nothing in this section sits on the
path of sections 4-7. Events follow NIP-01 (canonical serialization -
the id preimage is the interop contract), signatures BIP-340.

**8.1 RSN1 - the identity bridge.** **Exactly 276 bytes**:

    "RSN1"  handle(64 ascii hex)  nostrPub(64 ascii hex)
    seq(u64)  timestamp(u64)  edSig(64)  schnorrSig(64)

Both signatures cover one preimage: `"riptide-nostr-b" || the 148-byte
body`. `edSig` is ed25519 by the handle's key over the preimage;
`schnorrSig` is BIP-340 by the Nostr key over **SHA-256 of** the
preimage. A verifier MUST require both: one signature is an accusation
either key-holder could make about a stranger's other key; two make it
a two-sided statement.

Published in both worlds:

- **DHT**: a BEP44 mutable item under the handle's key at salt
  `"riptide-nostr"` (its own salt; RSH1 is untouched), BEP44 seq = the
  record's seq.
- **Nostr**: a kind-30078 (NIP-78) event, d-tag `"riptide.bridge"`,
  content = the record as lowercase hex, authored by the Nostr key.
  **The republish gate is normative**: a reader MUST require the
  record's `nostrPub` to BE the event's author pubkey - anyone can
  republish someone else's bridge, and a copy must verify as the
  original author's linkage, never the republisher's.

**8.2 Media on the Nostr wire.** Kind-1 notes carry riptide attachments
as one `r` tag per attachment: `["r", "magnet:?xt=urn:btih:<40 hex>"]`.
Strict on the way in; ordinary clients render a link.

**8.3 Policy (SHOULD, and the reference treats them as law):** nothing
dials a relay except by explicit user action; publishing the bridge is
its own click and the UI states it is public and permanent; NIP-42 auth
is never answered automatically; inbound media references are shown as
pointers, never auto-fetched. Nostr DMs are deliberately absent (NIP-04
is deprecated and needs AES; NIP-17 was out of scope).

## 9. Conformance

**9.1 Vectors.** `riptide/docs/protocol-vectors.json` carries 67 golden
vectors (one fixed identity: master `0x42*32`; every record above,
every derivation, DHT targets, the BEP44 buffers, both bridge
signatures, Nostr event ids) and 31 refusal vectors. The bundle is
regenerated from the oracle and re-EXECUTED on every push: signed
records re-verify, targets recompute, refusal vectors provably refuse.
An implementation is byte-compatible when it reproduces every golden
and refuses every refusal.

**9.2 Interop criteria**, cheapest first, each phrased so a run settles
it: (1) FEED - a head+chain published by one implementation is fetched,
walked, and signature-verified by another, and vice versa; (2) MEDIA -
an attachment seeded by one is fetched and content-verified by the
other; (3) BRIDGE - a third implementation resolves handle -> npub off
the DHT and npub -> handle off a relay, verifying both signatures and
the republish gate; (4) DM - a sealed intro from one opens a working
two-way secretstream session with the other; (5) the LAN, onion and
call rails, per their sections.

**9.3 What this spec does NOT cover**: the app-state payload text
(envelope only), UI behavior, storage layout, and the reference app's
polling cadences. Freshness windows and dial policy are SHOULD;
everything byte-level is MUST.
